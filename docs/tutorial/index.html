How the Meshtastic → Kafka pipeline actually works

A guided tour of every hop a sensor reading takes — from a radio packet in the field to a row in Postgres — told through the concepts that make it work and a real bug hunt that exercised nearly all of them.

8 sections, one glossary, one live incident. Grounded in docker-compose.yml, flink/decode_job.py, and registry/registry/.

1

The big picture

Strip away the services and this system does three things: get bytes off a radio network and onto Kafka, decrypt and classify each packet, and turn "this device exists and said X" into rows you can query.

Everything else — Django apps, Flink jobs, InfluxDB, S3 — exists to serve one of those three jobs. The trick to understanding the codebase quickly is to stop thinking about it as a list of services and start thinking about it as a pipe with three sections, joined by Kafka topics:

Note the two loops back into registry. It isn't only a registry that feeds the pipeline — it also receives from it: sightings and discovery events flow in to build the device/sensor catalog, and alarms flow in so they can be turned into an email to the right owner. And the config it publishes (quality_config.v1) is just the curated catalog, pushed back out to the jobs that need it.

The middle column — the Flink decode job — is the one piece that touches the actual radio protocol: encryption, packet framing, portnum classification. Everything to its right only ever reads and writes JSON on Kafka topics. That single fact is why section 6 treats the topic list as the system's real API surface, and why the incident in section 7 could take the whole pipeline down without a single service crashing.

2

Meshtastic in five terms

Before any of the pipeline makes sense, five Meshtastic concepts need to be solid. Everything downstream is just plumbing around these.

Mesh
A LoRa channel: a channel_id (its human name, e.g. SensorHub) plus a psk_b64 — the pre-shared key every device on that channel encrypts with. In this system a Mesh row is the unit an owner registers and pays attention to; it has exactly one owner and any number of devices.
Node vs. gateway
Both are physical Meshtastic devices, identified by a 32-bit device_id (shown in hex as !202d12ed, which is decimal 539824877). A node just talks on the mesh. A gateway also bridges the mesh to MQTT, so its traffic is what reaches this pipeline at all. In the registry, a Device row is always exactly one or the other — is_gateway xor is_node — never both, enforced by a database constraint.
ServiceEnvelope
The protobuf a gateway actually publishes to MQTT: a MeshPacket wrapped with channel_id and gateway_id. The MQTT topic itself encodes the same information, e.g. test/sensorhub/2/e/SensorHub/!19ba4462 — region / firmware / channel / gateway_id.
MeshPacket → Data → portnum
A MeshPacket carries either a plaintext decoded payload or an encrypted byte blob that unpacks into a Data message once decrypted. Data.portnum says what's inside — 67 is telemetry, 3 is position, and so on — and that number is how the decode job picks which protobuf schema to parse the payload with.
PSK and the "AQ==" shorthand
A real key is 16 or 32 raw bytes, base64-encoded. But Meshtastic also defines a 1-byte shorthand: 0 means no encryption, 1 (base64 AQ==) means "the well-known default channel key," and 2–10 mean that same default key with 1–9 added to its last byte. It looks like a secret; it isn't — it's a convenience for people who haven't set up a real channel key yet. Section 7 covers a bug caused by this shorthand not being implemented at all.

The encryption, concretely

Every encrypted payload uses AES in CTR mode. The interesting part is the nonce — the 16 bytes that make the same key produce different ciphertext for different packets. Meshtastic doesn't transmit a random nonce; it derives one from fields already on the packet:

nonce = packet.id.to_bytes(8, "little") + packet.from.to_bytes(8, "little")
cipher = AES(key_bytes) in CTR mode with that nonce
plaintext = decrypt(packet.encrypted)

mesh_things/codec.py — decrypt_packet()

This is safe precisely because the PSK is secret and the nonce doesn't need to be: CTR mode only breaks down if the same (key, nonce) pair is ever reused, and packet id + sender is unique enough in practice. It also means decryption is stateless and cheap — no per-device counter to track, which matters a lot once you see how many packets flow through the next section.

3

Antenna to Kafka

mqtt_kafka_bridge is deliberately dumb: it subscribes to the gateways' MQTT topics and republishes every ServiceEnvelope, byte-for-byte, onto mesh.telemetry.raw.v1. No parsing, no decryption — that's the next stage's job. The one subtlety worth knowing about is how those bytes travel through Flink's Kafka connector as a string:

# SimpleStringSchema decodes raw bytes through a Charset - UTF-8 would corrupt
# these protobuf packets, so ISO-8859-1 (byte-transparent) is used instead.
RAW_BYTES_CHARSET = "ISO-8859-1"

flink/decode_job.py

Protobuf bytes are arbitrary binary, not valid UTF-8. Decode them as UTF-8 and some byte sequences get silently mangled on the round trip. ISO-8859-1 maps every byte 0–255 to a distinct character one-to-one, so a string built from it and re-encoded back to bytes is guaranteed identical to the original — it's being used as a transport trick, not because anyone cares about Western European text encoding.

4

Two gates, three outputs

The decode job — Flink job name mesh-decode-decrypt — is where the interesting decisions happen. It's keyed by gateway_id, and connected to a broadcast stream built from two small, slow-changing Kafka topics: mesh.keys.v1 (which gateways are registered, and their mesh's PSK) and mesh.node_rejections.v1 (which specific nodes have been blocked).

"Broadcast state" is Flink's answer to a simple problem: the hot path — decoding a packet — can't afford a database lookup per packet, but it does need current config. So instead, every parallel task keeps a full, live-updated copy of these two tiny topics in memory. A packet's gateway either is or isn't in that in-memory map; no round trip required.

Gate 1 — registered gateways only

If a packet's gateway_id isn't in the broadcast state, it's dropped before decryption is even attempted. Registering a Device as a gateway through the registry is what publishes that gateway's entry to mesh.keys.v1 in the first place — which means nothing decrypts for a mesh until an owner has explicitly stood up a gateway for it.

Gate 2 — node rejection

Possession of the mesh's PSK is the entire authentication model here: any device that can successfully decrypt a packet is presumed to be a legitimate member of the mesh. There's no allow-list to populate up front. The rejection gate is the escape hatch for the obvious problem with that — an owner can block one misbehaving or compromised mesh_id:device_id pair without touching anyone else's key.

If a packet clears both gates, decrypt_packet tries AES-CTR decryption and a protobuf parse. Either can fail — wrong key, corrupt bytes, an unrecognized portnum — and the function returns None rather than raising. One bad packet should never take the stream down, so failure here is a value, not an exception.

One decrypt, three events

The part that's easy to miss on a first read: a single successful decode fans out into three separate Kafka writes, and none of them require a separate registration step:

# Unconditional: a successful decrypt proves mesh membership and
# creates the node as allowed-by-default on first sighting.

flink/decode_job.py — the comment above the sighting event

  • Decoded telemetry → mesh.telemetry.decoded.v1 — the actual payload, for postprocessing, alarms, and storage.
  • Device sighting → mesh.devices.v1 — "this device exists," opportunistically enriched with location (from a Position payload) or name/hardware (from a NodeInfo payload).
  • Sensor discovery → mesh.sensor_discovery.v1 — only for telemetry payloads, and only field names, never values. Discovery answers "what does this sensor measure," not "what did it measure just now" — a deliberate privacy boundary, not an oversight.
5

Sightings become a catalog

The decode job never touches Postgres. It just writes events. Two small registry consumers do the actual registration:

consume_device_sightings

Reads mesh.devices.v1 and upserts a Device row — is_gateway=False (a node), is_allowed=True by default — bumping last_seen on every sighting. Location and name/hardware fields get filled in opportunistically from the same event, but only if an owner hasn't already hand-edited them:

FieldAuto-filled fromSticky override flag
latitude, longitudePosition payloadlocation_overridden
name, short_name, hardware_type, roleNodeInfo payloadnodeinfo_overridden

The pattern is simple: automation fills in whatever an owner hasn't set, and the moment an owner sets it by hand, automation stops touching it. It's worth noticing this consumer only ever creates nodes. Gateways are never created this way — an owner registers a gateway explicitly through the API, and that registration is the same act that populates mesh.keys.v1 and turns Gate 1 open for that mesh. Cause and effect run in a specific order: register a gateway first, or nothing downstream ever fires.

consume_sensor_discovery

Reads mesh.sensor_discovery.v1 and upserts DeviceTelemetryVariant and Measurement rows against two global catalogs (TelemetryVariant, MeasurementType) shared across every mesh. This is how the system learns "device X reports environment_metrics with temperature and humidity fields" without anyone configuring it by hand — TelemetryVariant is keyed by wire-format message type, not verified physical hardware, since protobuf alone can't tell you whether that reading came from a BME280 or a BMP180.

6

Topics are the real API

Past the decode job, almost nothing in this system calls anything else directly. A Flink job reads a topic and writes a topic; a Django management command reads a topic and writes Postgres. That makes the topic list the actual interface contract — more so than any HTTP endpoint — which is exactly why a topic silently not existing (section 7) was able to take the whole pipeline down without a single stack trace pointing at the real cause for over an hour.

Two columns are worth a second look: everything a Flink job subscribes to as broadcast state — keys.v1, node_rejections.v1, quality_config.v1, postprocessing_config.v1 — is written by something other than a Flink job. If that something never writes to a brand-new topic, the topic never exists, and a Flink consumer can't create it either. That's the whole shape of section 7's first bug.

mesh.quality_config.v1 shows the pattern at its cleanest: there is no separate "rules" resource to manage. You edit the sensor catalog or a device through the normal REST API, registry publishes the change, and the Flink jobs pick it up as broadcast state. The catalog is the config — which is why mesh.rules.v1, a hand-published parallel source of the same thresholds, was retired rather than kept in sync.

7

Case study: three stacked bugs

The report was simple: a mesh should show a gateway and one other device, and the other device wasn't there. It took three separate, unrelated bugs — each hiding behind the last — to actually explain that.

Bug 1 — a topic that never existed

The decode job's jobmanager log showed the same cycle every 60 seconds: RUNNING → RESTARTING → RUNNING, forever.

Failed to list subscribed topic partitions due to
Caused by: java.lang.RuntimeException: Failed to get metadata for topics [mesh.node_rejections.v1].
Root cause

mesh.node_rejections.v1 only gets written to when an owner rejects a device — and nobody ever had. No producer had ever touched it, so it simply didn't exist. Kafka brokers can auto-create a topic on demand (auto.create.topics.enable=true here, confirmed), but that only applies to producers. Since Kafka 2.3 (KIP-361), a consumer subscribing to an explicit topic list does not trigger auto-creation — a deliberate guard against typos silently spawning junk topics. A pure-consumer topic that nobody has produced to yet is invisible to the one thing trying to read it.

Because Flink restarts a job's entire execution graph on any source failure, this took down raw-mesh-packets, gateway-key-config, and the whole decode-and-emit pipeline with it — every 60 seconds, for every mesh, not just this one.

Fix

Create the topic, and stop relying on "some producer will eventually write to it first": add a kafka-topics-init service to docker-compose.yml that pre-creates every topic the pipeline needs (idempotently), wired as a service_completed_successfully dependency ahead of every Kafka-touching service.

Bug 2 — a fix that looked like it worked

Once the job stabilized, the mesh in question suddenly had two node devices instead of one. That looked like success. It wasn't the right two.

The decode job's raw-packet source replays from earliest on every restart. The physical gateway involved had been reused across three different test meshes over the preceding days, and — because someone kept copy-pasting the same test PSK — all three registrations shared one literal key:

{"channel_id": "FAB26",     "mesh_id": "b096e8be-...", "psk_b64": "OEu8wB3A...MsaE="}
{"channel_id": "FAB26",     "mesh_id": "859fc619-...", "psk_b64": "OEu8wB3A...MsaE="}
{"channel_id": "SensorHub", "mesh_id": "cbaea59b-...", "psk_b64": "OEu8wB3A...MsaE="}

mesh.keys.v1 — three registrations of gateway !19ba4462, one reused key

What actually happened

Old packets from the earlier, unrelated test meshes decrypted successfully — with the same key — and got attributed to whichever mesh currently owned that gateway ID at replay time. The count went from one device to two, which read as progress. Neither new device was the one from the original report.

The lesson generalizes past this codebase: when a fix changes the numbers, check that it changed the specific thing you expected, not just that the state moved. "More devices showed up" and "the right device showed up" are different claims.

Bug 3 — the real device, and a bug hiding a bug

The actual device (!202d12ed, decimal 539824877) was live and reachable — its uplinks showed up in a decrypted MQTT tap every minute — but it never appeared in Postgres. The taskmanager logs explained why, once you got past the first exception:

Traceback (most recent call last):
  File "mesh_things/codec.py", line 33, in decrypt_packet
    data.ParseFromString(decrypted_bytes)
google.protobuf.message.DecodeError: Error parsing message

During handling of the above exception, another exception occurred:

Traceback (most recent call last):
  File "mesh_things/codec.py", line 36, in decrypt_packet
    log.warning("Decryption failed", error=str(e))
  ...
TypeError: CustomPrint.print() got an unexpected keyword argument 'flush'
Two bugs, stacked

The real one: the mesh's registered PSK was that same stale, reused test key — not the device's actual channel key, which was AQ==, Meshtastic's "use the default channel key" shorthand. Decryption with the wrong key produces garbage bytes, and ParseFromString correctly rejects them.

The one that hid it: codec.py's own error handler called structlog's log.warning(...) — which crashes inside PyFlink's UDF runtime. decode_job.py already had a documented workaround for this exact incompatibility (_udf_log, using plain print()); codec.py had just never been updated to match. Every real decode failure was arriving as a confusing second-order TypeError instead of the actual DecodeError.

And underneath both: decode_psk("AQ==") had never actually implemented the shorthand. The code's own comment said so — "we don't expand the real default PSK yet" — so even the correct key would not have worked without a code change.

Fix

Implemented the real shorthand (index 1 = the literal default key from Meshtastic's own channel_pb2.pyi; 2–10 = that key with n-1 added to its last byte), removed the two structlog calls from the UDF's hot path, rotated the mesh's PSK to AQ== through the actual Django/Kafka-publisher code path, and rebuilt the Flink image. Verified by watching last_seen advance across two separate live uplink cycles — not just checking that a row existed once.

What this teaches

  • Read the actual error, not the symptom. "Devices aren't registering" was three unrelated root causes wearing one symptom.
  • A crash can hide a more useful error underneath it. The TypeError from the logging call was itself a real bug — but chasing it first would have missed the DecodeError it was masking.
  • Verify the specific claim, not the general shape. "A device appeared" is not the same claim as "the reported device appeared."

Field guide

The commands that actually did the diagnosis above, kept here for next time.

Inspect Kafka

# list every topic
docker compose exec kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server kafka:29092 --list

# dump a topic from the start (Ctrl-C or --timeout-ms to stop)
docker compose exec kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server kafka:29092 --topic mesh.devices.v1 \
  --from-beginning --timeout-ms 10000

# message count without dumping the payloads
docker compose exec kafka /opt/kafka/bin/kafka-get-offsets.sh \
  --bootstrap-server kafka:29092 --topic mesh.devices.v1 --time -1

Inspect the Flink job

# job lifecycle: RUNNING / RESTARTING / the exception that caused it
docker compose logs jobmanager --since 30m | grep -iE "RUNNING|RESTARTING|Caused by"

# per-packet errors happen on the taskmanager, not the jobmanager
docker compose logs taskmanager --since 10m | grep -iE "Failed to decode|Traceback"

Inspect the registry

docker compose exec postgres psql -U meshtastic -d meshtastic_keys -c \
  "SELECT device_id, is_gateway, is_node, is_allowed, last_seen
     FROM devices WHERE mesh_id = '<mesh-uuid>';"

Node ID math

Meshtastic shows node IDs as hex (!202d12ed); the registry stores them as decimal device_id. Converting by hand beats guessing:

python3 -c "print(int('202d12ed', 16))"
539824877

Inspect the data-quality checks

# what config the Flink jobs currently hold (compacted = live state)
docker compose exec kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server kafka:29092 --topic mesh.quality_config.v1 \
  --from-beginning --property print.key=true --timeout-ms 10000

# alarms as they fire, from either tier
docker compose exec kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server kafka:29092 --topic mesh.telemetry.alarms.v1 --timeout-ms 30000

# run a batch check on demand instead of waiting for the scheduler
docker compose exec quality_worker python -c "
from quality_worker import celery_app
from quality_worker.tasks import check_completeness
print(check_completeness.apply(args=['<device-uuid>']).get())"

No alarms at all usually means nothing is configured yet: with no valid_min/valid_max set on the device's own measurement there's no range check, and with no configured interval there's no absence timer — deliberately, since a guessed interval produces meaningless alarms. See data-quality.md.

Glossary

blueprint
A reusable, versioned recipe for derived channels: input slots and ordered steps, each running an algorithm, so one algorithm can span several sensors and a step's outputs feed later steps. Attaching it to a device binds the slots to that device's channels and gives it the device's own calibration.
broadcast state
Flink's mechanism for giving every parallel task a full, live-updated copy of a small config stream, so the hot path never needs a lookup per record.
channel (data-quality sense)
One addressable timeseries, written "<measurement>.<field>" — e.g. environment_metrics.temperature. Not to be confused with a Meshtastic radio channel.
default-open
The security model where any device that can decrypt with the mesh's PSK is presumed legitimate; blocking is opt-out (rejection), not opt-in (allow-listing).
gateway
A Meshtastic device that bridges its mesh to MQTT. Its registration is what lets the decode job decrypt anything for that mesh at all.
KIP-361
The Kafka change (2.3+) that stopped consumers from auto-creating topics on subscribe — only producers can still do that.
PSK
Pre-shared key for a mesh's AES encryption. Either 16/32 real bytes, or a 1-byte shorthand (0–10) for "no encryption" or a well-known default key.
publish vs reading interval
How often a device transmits vs how often it samples. They diverge once telemetry is batched, which is why "stopped publishing" and "stopped reading" are two separate fault checks rather than one.
sighting
The event emitted on every successful decrypt, proving mesh membership and upserting a Device row as allowed-by-default.
